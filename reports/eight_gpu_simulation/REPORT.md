# 8 卡节点单卡故障模拟

模拟对象是当前工作区代码，未修改生产采集逻辑，未连接真实服务器、读取真实凭据或执行真实 GPU 命令。

## 输入与边界

- 8 张虚拟 GPU，PCI 地址为 `0000:01:00.0` 到 `0000:07:00.0`，以及 `0000:1b:00.0`。
- 故障卡为第 8 张（已有缓存时编号 `7`），注入截图中的错误文本：

  ```text
  Unable to determine the device handle for GPU0000:1B:00.0: Unknown Error
  ```

- 主场景假定其他 7 张卡的逐卡查询成功，其中 3 张有计算进程、4 张空闲。
- 截图本身不能确定命令退出码、是否已经退出、是否存在 D 状态进程，也不能证明其他卡的逐卡查询可用。退出码 `255`、进程残留、PCI 设备消失、SSH 中断和关闭通道阻塞均为明确注入的模拟条件。
- SSH 传输层由本地假通道替代，真实执行项目的 `_run_command`、采集器、重试退避、Flask API 和后台循环。没有模拟真实 NVIDIA 驱动、Linux 内核或 SSH 服务端。
- 退避场景使用虚拟时钟：虚拟 0～600 秒共执行 601 轮，不必实际等待 10 分钟。单卡无响应场景则保留生产环境的 5 秒本地超时，实际等待约 5 秒。

## 实测结果

| 场景 | 当前程序表现 | 结论 |
| --- | --- | --- |
| 1 张卡返回 Unknown Error，其他卡正常 | API 返回 8 张卡；7 张有有效数据，1 张带 `error`；故障卡各指标和 `users` 为 `null`；4 张计为空闲 | 单卡错误隔离有效；节点不置顶层 `error`，前端显示 degraded |
| 首次启动时该卡就报错 | 仍返回 8 张卡；故障卡编号使用 `0000:1b:00.0` | 不依赖成功查询才能列出 PCI 目录中可见的坏卡 |
| 失败持续 10 分钟，进程正常退出 | 坏卡只在虚拟第 0、30、90、210、450 秒查询；正常卡每轮继续查询；无全卡 `nvidia-smi` 枚举 | 退避生效；不会每秒重新查询坏卡 |
| 查询不返回，本地超时后远端仍残留 D 状态进程 | 首轮约 5 秒返回，其他 7 张卡有效；后续 6 轮及模拟监控重启均跳过坏卡 | 残留检查生效；模拟残留始终为 1 个，坏卡新查询总计 1 次 |
| 发现无目标的残留 `nvidia-smi` | 只执行一次进程检查；暂停整个节点，返回节点错误和空列表 | 无法定位残留查询时采取整节点保护；健康卡也停止采集 |
| PCI 发现为空且无缓存，全卡枚举也失败 | 10 分钟内只在 0、30、90、210、450 秒执行全卡枚举 | 有节点退避，但没有失败次数上限或永久禁用标记 |
| SSH 中断后，坏卡又不在 PCI 目录中 | 节点失败先清空缓存；恢复后只返回 7 张卡，坏卡消失且无单卡错误提示 | 复现已知设备记录丢失问题 |
| 所有逐卡查询都返回错误 | 8 张卡均不可用，空闲数为 0；节点级 `error` 仍为空 | 逐卡隔离无法让失败的指标查询恢复；需结合各卡错误判断可用性 |
| 某个通道的 `close()` 阻塞，另一台节点正常 | 正常卡和正常节点已完成查询，但全局缓存不更新；3 次 API 请求均返回 HTTP 200 和旧缓存；未开启下一轮 | 复现关闭阶段缺少硬期限、慢任务阻塞全局发布的问题 |

### 主场景的模拟通道计数

在虚拟 10 分钟、601 轮采集中：

- 共打开并关闭 **10,222** 个模拟通道，剩余 **0** 个，峰值同时存活 **4** 个。
- 这是历次短命令的累计数量，不是同时保持 10,222 个连接。
- 正常卡指标查询 `7 × 601 = 4,207` 次，坏卡指标查询 5 次，总计 4,212 次。
- 计算进程查询 4,207 次；坏卡指标失败后，不再对它查询计算进程。
- 虚拟第 750 秒恢复该卡后，返回 8 张有效卡，空闲数从 4 恢复为 5。
- 上述关闭计数来自模拟传输层，不能证明真实 SSH 故障下所有通道必然关闭。

### 关闭通道阻塞场景的具体证据

- 只为此场景将本地超时缩短为 0.05 秒，并让故障通道的关闭动作阻塞至少 0.25 秒。
- 阻塞期间存在 1 个尚未关闭的模拟通道；同一卡的新查询次数仍为 1，没有持续启动新一轮。
- 另一台健康节点的新 GPU0 利用率为 60%，API 却仍返回旧缓存中的 10%。
- `CACHE_UPDATED_AT` 不变，但 API 仍返回 HTTP 200，且响应没有缓存采集时间字段。
- 解除模拟阻塞后，后台循环完成本轮发布，利用率变为 60%，通道全部关闭。
- 该场景证明项目缺少对关闭阶段阻塞的独立约束；没有证明真实 Paramiko 或真实服务器已经出现这一故障。

## 前端验证

将模拟生成的真实 API 结构输入生产 `static/js/main.js` 的函数，验证：

- 数据表保留 8 行。
- 故障卡显示 `Unavailable`、灰色、`-/- GB`，错误文本保留。
- 故障卡不带空闲样式，不进入空闲筛选结果。
- 空闲统计为 `4 / 8`。
- 节点状态为 degraded。

这里验证的是展示函数输出，未进行浏览器页面截图或视觉验收。

## 本次发现的重点问题

1. **通道关闭阻塞会拖住整个采集轮次**，其他正常节点也无法发布新数据；线程池不会强制取消任务。
2. **旧缓存没有向前端暴露真实采集时间**，采集卡住时 API 仍可成功返回；前端的更新时间是取缓存的时间，旧空闲状态可能继续显示。
3. **节点级失败会丢失设备清单**，坏卡随后从 PCI 目录消失时，恢复后可能被静默遗漏。
4. **残留进程保护是暂停采集，不是清理进程**；无法识别目标时健康卡也会暂停。

这些是对现有行为的观察，本次没有修复生产代码。模拟断言通过意味着观察符合当前实现，不意味着上述缺口已经解决。

node tests/check_eight_gpu_frontend.cjs

node tests/test_frontend.cjs
